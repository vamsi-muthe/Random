10. Validation Results (Phase 3)

Measured on 2026-08-04. The decision no longer rests on inference.

Why this exists. Everything in pages 1-9 was modelled or inferred from vendor benchmarks. A reviewer correctly pushed back that the option being selected was the one option never evaluated on our corpus. This page is that evaluation.

Method

Same 18 SIAs and 84 entities as the Phase 1 test, same four validation layers (self-match exclusion, file-type filter, co-occurrence, LLM relevance judge). Only the retrieval mechanism changed: a Sonnet 4.6 agent with grep, read_file and list_directory scoped to each SIA's tier-0 repositories, temperature 0, prompt caching on, 7 turns.

Harness: scripts/agentic_eval.py. Raw data: results/results_test_h_agentic.json.

Corpus: 20 SIAs, 18 tested

The corpus is 20 SIAs / 85 entities. Both G and H ran on 18 / 84. The two exclusions are properties of the corpus rather than of any retrieval method, so they apply identically to every option:

SIAReason
nitro_encryptionEntity extraction yields 0 entities - the source SIA is an unfilled template with every field set to -. Nothing to retrieve.
self_service_sso1 entity, and it is sso-configuration - the repository's own name. Filter 1 (self-match exclusion) rejects every candidate by construction.
A validation-design flaw this exposed. Running the harness on self_service_sso anyway, the agent located CODEOWNERS - genuinely the file that governs SSO-config approvers, i.e. the correct answer - and all 8 matches were still scored noise. The self-match filter keys off the entity name rather than the term actually searched. Logged as a risk.
