Example: How KB-Docs + KB-Code work together

KB-Docs (Stratus docs): "Teleport auth requires FedRAMP + US persons + Okta SAML"

KB-Code (teleport repo chunks): "These are configured as: fedramp, usPersonsRequired, okta_group"

LLM combines both: keywords = [fedramp, usPersonsRequired, okta_group, publicly_accessible]

Docs gives CONTEXT (why it matters). Code gives SYNTAX (what to grep). Together = best keywords.

8/16

Two Quality Gates at Two Stages

The 47% noise rate already benefits from reranking. Without it, noise would be ~60-70%.

Existing

Bedrock Reranker (Cohere)

Operates on: KB chunks (text)

Purpose: "Which KB chunks are most relevant to this entity?"

Effect: Better chunks = better keywords = less grep noise downstream

Improves keyword QUALITY

then
New

LLM Relevance Judge

Operates on: Grep results (code files)

Purpose: "Is this code file evidence about the proposed change?"

Effect: Filters files that match keywords but aren't about THIS change

Improves evidence QUALITY

They don't overlap - they're complementary.

Reranker ensures KB gives the RIGHT vocabulary.
Judge ensures grep results are ABOUT the proposed change.
Even with perfect keywords, grep returns all files containing that keyword - some relevant, some not.

KB's Superpower: Cross-Repo Discovery

KB finds related code in repos the developer never mentioned.

SIA says:

"Making Teleport publicly accessible"

Tier 0 repos: teleport

Developer didn't mention authentication.

Didn't mention sso-configuration repo.

KB discovers:

Query: "Teleport public access authentication"

teleport/main.tf:

publicly_accessible = false

sso-configuration/teleport-prod.yml:

fedramp: true, usPersonsRequired: true

How it works: All 31 repos live in ONE vector space (AOSS). A single query surfaces semantically related chunks regardless of which repo they came from. "Teleport public access" returns chunks about Okta auth from sso-configuration because they're semantically close.

Why grep alone can't do this: Grep CAN search all repos. But it needs a keyword first. The SIA says "making Teleport publicly accessible" - nothing about Okta. Nobody tells grep to search for okta or usPersonsRequired. KB bridges the gap: semantic search for "Teleport access" surfaces Okta-related chunks, which gives us keywords the SIA never mentioned.

The real discovery: Not WHERE to look (grep can search everywhere), but WHAT to look for that you didn't know was relevant.
10/16

Proven Pattern: ai-sre Does This Today

The ai-sre orchestrator already uses KB + code search in parallel in production.

ai-sre (production)

  • Documentation agent queries KBs
  • Sidekick triggers GitLab CI for code analysis
  • Orchestrator synthesizes all findings
  • LangGraph + AgentCore Runtime
  • Phased: understand -> gather -> act

Our SIA pipeline (Option G)

  • KB-Code + KB-Docs for vocabulary
  • GitLab API search with KB keywords
  • Synthesis agent reasons over evidence
  • Deterministic orchestrator + LLM workers
  • Phased: extract -> align -> synthesize

Key difference: ai-sre's Sidekick is an agent that NAVIGATES code (reads files, follows imports, 30min loop). We front-load the thinking in KB, so search is just keyword lookup (2s). Both hand results to a reasoning agent at the end - we just get there faster.
